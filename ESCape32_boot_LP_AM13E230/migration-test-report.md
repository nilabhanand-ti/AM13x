No `.cproject`/`.project`/`.ccsproject` edits. [T1, T2]
- `linker/boot_ticlang.cmd`: added `palign(16)` to `.text`, `.rodata`, `.TI.ramfunc` (was `palign(4)`) and `.data` (was `palign(4)`), following the SDK linker file's `palign(8)` convention and sized for the 128-bit flash ECC word. The program load failed with "File Loader: Memory write failed" because the ELF load segments were split mid-flash-word: segment 0 ended at 0x7CC, the `.TI.ramfunc` load image started at 0x7CC, and `.rodata` started at 0xAB4. Only 0x0–0x7CB was programmed. Now all segments are 16-byte aligned. Code symbols are unchanged; the `.TI.ramfunc` load address moved 0x7CC → 0x7D0. Updated `config.js` `addr.ramfuncLoad` to match, added a `__ramfunct_load__` symbol cross-check, and updated the plan's T1 / debug-helper addresses. [T1]
- `specs/t02_register_state.spec.js` + `config.js` (`bits.FRI_FRDCNTL_WS0_MODE`): the FRI check now derives the read wait states the way `DL_FRI_getReadWaitStates()` does (WS0_MODE=1 → 0 wait states; `DL_FRI_setReadWaitStates(0)` sets WS0_MODE and leaves RWAIT=2). It requires CACHE_EN only when WS0_MODE=0. On hardware, a debugger write of 0x6 to FRD_INTF_CTRL reads back 0x2 with WS0_MODE=1, and 0x6 with WS0_MODE=0. A breakpoint right after `SYSCFG_DL_FLASH_init()` (0x47A) showed CACHE_EN=0 although the generated code calls `DL_FRI_enableCache()`. So the hardware gates the cache in zero-wait-state mode; this is not a firmware defect. The plan T2 FRI pass criterion was updated to match. (The spec expected the raw RWAIT field to be 0 and CACHE_EN to be 1.) [T2]
- `src/io.c` `initio()` (`IO_UC4` branch) + `mcu/AM13E230X/config.h` (new `IO_UC4_BRD64`): after `SYSCFG_DL_SIG_UART_UC4_init()` / `DL_UART_changeConfig()`, the firmware now sets the UC4 divisors with `DL_UART_setBaudRateDivisor(SIG_UART_UC4_INST, IO_UC4_BRD64 >> 6, IO_UC4_BRD64 & 0x3f)`. `IO_UC4_BRD64` is computed from `CLK` (MCLK 32 MHz) and `SIG_UART_UC4_BAUD_RATE` using SysConfig's rounding, which gives IBRD 52 / FBRD 5 = 38 403 baud (+0.008 %).
  - Why: UC4 ran at 76 800 baud. On hardware, UC4 CLKSEL = BUSCLK with CLKDIV /1. A host at 76 800 baud got correct PROBE/INFO answers, and debugger-written TXDATA bytes arrived doubled in rate at 38 400 baud. So the UC3–UC5 segment (0x4064xxxx) is clocked from MCLK. The SDK SysConfig metadata (`getBUSCLKFreq("UART")` → SemiMCLK) computed 26/3 for 16 MHz.
  - Scope: no change to the `.syscfg`, pins, or clock tree. Generated files are untouched. Release_PA26/Release_TIMER are unaffected (the code is under `#ifdef IO_UC4`).
  - Side effect: `initio()` is now out of line, so the Debug symbols moved. `Reset_Handler` 0x2AC→0x328, `recvbuf` 0x4EC→0x518, `recvval` 0x6B6→0x6E2, `Default_Handler` 0x5CE→0x5FA, `.TI.ramfunc` load 0x7D0→0x800, vector[1] 0x2AD→0x329. FLASH_BOOT use is 0xB30 of 0x1000. The test `config.js` `addr`/`symbolChecks` and the plan addresses were updated to match.
  - Reviewer: (1) this works around an SDK SysConfig clock-domain assumption; consider reporting it to TI. (2) Confirm the UC0 (`IO_PA2`) and TIMG4 (`IO_TIMER`) clock assumptions (SemiMCLK) on silicon when T12/T13 can be run. [T3, T4, T5, T6, T7, T8, T9, T10, T11]
- `lib/debug.js` `refreshConnection()` (test project): now always forces `disconnect()` + `connect()` after a BOOTRST. Before, it returned "ok" whenever the target still reported connected. On hardware after a firmware BOOTRST, FPB_CTRL read 0x10000080 (ENABLE = 0). As a result, the T10 `restart()` (run to main) never halted and hit the 60 s scripting timeout. In the same state, multi-word reads returned word 0 repeated: the T9 slot read as `{M, M, M, FF}`, although single-word reads showed `{M, 0, FFFFFFFF, FFFFFFFF}`. A reconnect restores FPB_CTRL = 0x10000081 and correct block reads. The plan's debug-helper BOOTRST rule was updated. Firmware unchanged. [T9, T10, T11]
- `specs/t10_app_handoff_level0.spec.js` + `config.js` (`bits.SYSTICK_CTRL_CLKSOURCE`): the hand-off check now requires `SysTick CTRL & ~0x4 == 0` (ENABLE and TICKINT clear) instead of `CTRL == 0`. CLKSOURCE is read-as-one on this core: SYST_CALIB = 0xC0186A00 (NOREF = 1), CSR resets to 0x4, and a debugger write of 0 reads back 0x4. `done:` already writes `SysTick->CTRL = 0`. The plan's T10 pass criterion was updated. Firmware unchanged. [T10]
